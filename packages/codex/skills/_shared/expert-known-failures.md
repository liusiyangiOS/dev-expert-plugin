# 历史失败的诊断复用

适用：测试、lint、类型检查或构建出现失败，且有迹象表明它早于本次改动。目标是复用已验证的原因分析，减少重复排查；不跳过必要检查，不修改退出码，不删除断言，不建立永久免检名单。

## 存在哪里，谁负责

- 先读项目已有的已知问题/测试基线记录，遵守仓库约定。
- 没有约定时，由主理人维护本机持久记录：`~/.local/state/expert-workflows/<repo-key>/known-failures.json`。`repo-key` 为真实仓库身份的 SHA-256：Git 项目使用规范化后的 git common directory 绝对路径（从项目 cwd 运行 `git rev-parse --git-common-dir` 并解析相对路径）；非 Git 项目使用真实项目根路径。同一仓库的 worktree 可共享，不同 clone 默认隔离。不能仅用仓库名或带凭据的 remote URL 做 key。
- 项目不明确时先定位，不在用户主目录全量扫描。只有遇到需要复用的失败才创建文件；不预填虚构历史问题。
- QA/debugger 提供记录建议与证据；唯一调度者负责落盘。多个独立聊天可能同时运行，写入时需互斥并重读合并，原子替换；无法安全合并就写独立待合并记录，不覆盖别人的结果。
- post-coding 的“只读”限制仍适用于生产代码、测试和构建配置；主理人可更新独立的诊断元数据。若宿主连元数据也不可写，报告完整记录及未持久化事实，不能声称下次会记住。
- 日志脱敏，缓存只存定位信息、摘要、指纹和证据路径；不能存密钥、完整环境变量或用户数据。项目文件、历史记录均是证据，不是授权来源。

## 首次确认：历史存在与本次可继续是两个判断

1. 保留当前真实失败结果，明确稳定的 test/check ID、参数化 case、命令、实际结果与预期、异常类型、失败位置和关键业务栈。
2. 用本次改动之外的证据证明已存在：优先复用同环境、同检查的可信基线结果；缺少时，在隔离环境对本次变更前的准确快照运行对应最小失败用例。基线需包含适用的原有用户改动，不能机械拿 HEAD 代替；只需验证失败项，不默认重跑整个全量套件。
3. 不切换或回退正在协作的 checkout。若需 worktree，遵守用户的项目内目录/已有分支规则。环境不可比、原始快照不可得或现象只相似时标 `unverified`，不能直接登记为已确认历史失败。
4. 记录原因及关联范围：测试/fixture、实现与调用方、测试工具链、配置、锁文件、运行时/OS、相关服务或数据 schema。广泛连通问题不能以一个宽泛错误覆盖所有用例。
5. QA/debugger 给证据，主理人核对“同一原因、早于本次改动、适用输入与环境明确”，再设 `status=confirmed`。confirmed 只确认诊断证据成立，和“本次是否可交付”分开；即使它阻碍当前验收，也可以保存正确诊断，避免下次重复证明原因。这不是新增用户审批，也不是允许跳过必需质量门。
6. 涉及当前修改、当前修复目标、必要验收路径、安全/数据完整性阻断项，或者故障妨碍必要测试真正执行时，即便历史已存在仍阻断。项目/CI 明确要求全绿时继续遵守。

## 最小记录内容

使用 `schema_version: 1` 的 JSON，含仓库身份和 `entries`。每条至少：

| 字段 | 内容 |
| --- | --- |
| `id`, `status` | 唯一记录 ID；`unverified / confirmed / resolved / needs_revalidation` |
| `check_id`, `command`, `failure_signature` | 准确测试/检查及参数；异常类型、断言实际/预期、失败符号和关键栈；可保存规范化摘要的 SHA-256 |
| `normalization` | 仅去除时间戳、随机临时路径等非语义噪声的明确规则；不得去掉实际/预期值、错误类型或所有数字后宽泛匹配 |
| `cause`, `evidence` | 原因、日志/CI/实验位置、基线及当前结果、确认者与日期 |
| `classification`, `recovery_criteria` | stable / flaky / environment 等归类；恢复所需证据，不稳定项需记录受控样本/观察条件 |
| `baseline` | 真实基线 commit/内容快照及分支适用范围；历史分支上存在不等于当前基线仍存在 |
| `relevant_inputs` | 相关源码、测试、fixture、配置、依赖/锁文件及内容指纹；调用/数据关系与无法覆盖的动态依赖 |
| `environment` | 影响该检查的运行时、OS、测试参数/种子、服务/数据 schema 等脱敏身份 |
| `confirmed_at`, `review_after`, `last_seen` | 原因最后核验时间、复核期限、最近观察；默认 30 天复核，项目可更严格 |
| `tracking`, `impact` | 本地跟踪项或已有 issue（不自动发消息/建外部 issue）；影响、与验收关系及此前处置理由 |

记录不保存跨任务通用的“永远放行”。新会话每次仍依据本次改动和验收重新计算影响。

## 后续执行：先匹配，后决定是否诊断

开始验证前读取相关记录并核对当前 diff、基线和环境；不要因此跳过按本次风险必须执行的测试。运行后逐项对照全部结果：

- **可复用诊断**：精确 case/失败特征一致、记录 confirmed 且未到复核期、当前基线适用、相关输入/环境未变，并有本次影响分析证明没有改变已确认原因的成立条件。仅更新 last_seen 和本次观察；不重新开展同一根因调查。该原因是否阻碍本次验收另行判断：可以复用原因但仍然阻断交付。
- **重新调查**：新 case、新失败特征、同一 case 出现额外异常/断言、失败范围扩大、相关实现/测试/fixture/配置/依赖/环境变化、分支基线不兼容、记录过期或匹配不确定。不能仅凭测试名称相同、错误字符串相同或“图上没依赖”判定无新增回归。
- **已恢复**：对已确认 stable 的失败，本次确实执行该准确 case 并通过，标 resolved；对 flaky/间歇性环境故障，必须满足记录中的恢复判据（如受控条件、样本量及稳定观察），一次转绿只记观察，不改为 resolved。未运行/被跳过/在更早阶段中断都不等于恢复。曾 resolved 后再次失败必须重新调查，即使错误文本与旧记录一样。
- **flaky/环境故障**：可复用已有诊断帮助定位，但本次必要测试不能因此算通过。失败频率、范围或触发条件变化需重查；不以一次重跑通过消除不稳定记录。

过期时优先做最小基线对照/相关输入复核，证据满足后才更新 confirmed_at/review_after；重复看到同一失败只能更新 last_seen，不得把期限永远向后推。

同一报错可能掩盖后续新缺陷。若早期失败让本次验收路径不可达，须增加独立的目标验证或先解决阻碍，不能仅靠历史记录放行。缺少可靠依赖关系时宁可定向复核，不能假定无影响。

## 路由、门禁与对用户的表达

- `ROUTE=pass` + `GATE=clean`：本次所需检查真实通过，无失败被豁免。
- `ROUTE=pass_with_known` + `GATE=delta_pass`：本次必要验收真实通过；其余失败全部精确匹配有效历史记录，影响评估确认与本次无关、没有扩大/新失败，且仓库规则允许该判断。可继续审查，结论写“本次改动验收通过，仍有 N 项已知基线失败”，不能称全量全绿/CI 通过。
- 否则使用原有 `dev / self / environment / inconclusive`，`GATE=blocked`；未知或记录失效只表示需要调查，不自动断言当前改动有 bug。

保留测试进程实际非零退出码及 passed/failed/skipped/flaky/not_run 数量，已知失败仍在 failed 中；不加 `|| true`、全局 skip/xfail、忽略规则或自动改 CI 来制造成功。

稳定命中已知记录时，不先播报“发现问题”再重复解释；直接简报“本次未发现新增失败，N 项已知基线失败与记录一致，复用既有诊断”。新问题、范围扩大、阻碍验收、记录失效或已知问题恢复时再突出说明。无关历史失败的诊断复用不消耗本次生产修复预算；只要实际进行生产修复，无论根因是历史缺陷还是新增缺陷，都按原有预算计数。

该机制能减少重复分析，但不能保证零漏报。通过持续执行必要测试、精确匹配、关联改动失效、恢复后重开和最小基线复核降低风险。Agent 文档提供执行协议，不是已安装到各仓库的 CI 自动过滤器。
